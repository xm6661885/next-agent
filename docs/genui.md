# Generative UI：AI 对话中的动态交互界面

## 一、这是什么？

Generative UI（生成式用户界面）是一种让 AI 在聊天回答中直接生成可交互界面的能力。

传统 AI 聊天主要输出 Markdown 文本、代码、图片等静态内容，而 Generative UI 允许 AI 根据当前对话内容，动态生成具有交互能力的界面。

例如，AI 在回答问题时，可以直接嵌入：

- 按钮、滑块、输入框、复选框、下拉菜单
- 表单、卡片、列表、表格
- 图表、数据可视化、交互式 SVG
- 日期选择器、筛选器、选项卡
- 动态计算器、配置面板
- 可以直接触发后续 AI 对话的交互组件

**它不只是把 HTML 或 SVG 显示在消息里，而是让 AI 生成的界面成为聊天系统的一部分。**

用户可以直接在 AI 的回答中操作这些界面，而不是只能阅读文字。

这里介绍的是参考 ChatGPT 交互式回答体验的产品概念，不代表其全部内部实现细节。

## 二、核心能力

### 1. 动态 UI 生成

AI 可以根据对话内容，自行决定是否需要展示交互界面，以及需要什么样的界面。

例如：

用户问：

> 帮我计算一下不同贷款金额的月供。

AI 不一定只返回计算公式，而是可以直接生成一个贷款计算器。

界面可能包含：

- 贷款金额输入框
- 贷款期限滑块
- 利率输入框
- 每月还款金额
- 总利息显示
- 还款趋势图表

这些界面是针对当前问题动态生成的，而不是预先写死的页面。

对于普通问题，AI 仍然可以正常使用 Markdown 回答，不需要强制生成 UI。

### 2. 本地交互与状态管理

生成的 UI 不只是静态展示。

用户可以直接操作控件，界面根据操作实时更新。

例如：

- 拖动滑块，实时更新计算结果
- 切换选项卡，显示不同内容
- 选择筛选条件，更新表格
- 勾选复选框，改变配置
- 点击按钮，修改局部界面状态
- 输入数据，实时展示统计结果

**这类交互不需要每次都调用大模型 API。**

UI 可以拥有自己的临时状态和交互逻辑。

例如，一个 AI 生成的计算器可以在本地完成计算，用户每次修改数字都不需要重新请求 AI。

### 3. 与 AI 对话联动

这是 Generative UI 非常重要的能力。

**生成的 UI 可以主动向当前 AI 对话发送消息。**

例如，AI 回答：

> 你想开发哪种应用？

同时生成三个按钮：

- Web 应用
- 桌面应用
- 移动应用

用户点击「桌面应用」后，系统可以直接将选择结果作为新的对话消息发送给 AI。

AI 随后根据这个选择继续回答。

用户不必手动输入「我选择桌面应用」。

这种交互可以包含更复杂的内容。

例如，一个表单包含：

- 项目类型
- 预算
- 开发周期
- 技术偏好

用户填写完成后，点击「生成方案」。

界面就可以将所有选择提交给当前对话，AI 根据表单数据生成后续内容。

因此，Generative UI 不只是一个可交互的网页片段，它还可以作为**用户与 AI 之间的交互入口**。

### 4. 宿主应用动作

除了本地交互和发送 AI 消息，生成的 UI 还可以触发宿主应用允许的操作。

例如：

| 功能 | 说明 |
|---|---|
| 发送对话消息 | 向当前 AI 会话提交新的用户输入 |
| 复制内容 | 将文本或数据复制到剪贴板 |
| 打开链接 | 使用宿主应用打开指定网页 |
| 打开详情 | 打开商品、文件或其他对象的详情 |
| 提交选择 | 将表单或控件状态提交给宿主 |
| 更新界面 | 修改当前交互组件的状态 |
| 请求 AI 处理 | 将当前操作结果交给 AI 继续处理 |

这些能力由宿主应用决定，并不代表 AI 生成的界面拥有任意系统权限。

### 5. 数据可视化

Generative UI 可以直接展示可视化内容，而不只是使用 Markdown 表格。

例如：

- 折线图
- 柱状图
- 饼图
- 散点图
- 进度条
- 仪表盘
- 时间线
- 交互式数据面板

这些图表也可以具有交互能力。

例如用户切换「最近 7 天」「最近 30 天」时，图表可以直接切换数据。

还可以通过点击某个数据点，查看详细信息，甚至将选中的数据发送给 AI 进一步分析。

### 6. 复杂组合界面

Generative UI 不局限于单个按钮或者输入框。

AI 可以在一条回复中生成由多个元素组成的完整界面。

例如，一个任务管理界面可以包含：

- 顶部标题
- 搜索框
- 状态筛选器
- 任务列表
- 任务详情卡片
- 完成状态复选框
- 新建任务按钮

多个组件之间可以共享状态、相互影响。

因此，生成的内容可以接近一个小型应用，而不只是简单的表单。

## 三、交互类型

从用户体验上，可以将 Generative UI 的交互分为三种。

### Local Interaction（本地交互）

用户操作仅影响当前 UI。

例如：

- 滑块调整
- 表单输入
- 选项切换
- 数据筛选
- 本地计算

不需要向 AI 发送消息。

### Conversation Interaction（对话交互）

用户操作会触发新的 AI 对话。

例如：

- 点击「继续分析」
- 点击「选择方案 B」
- 填写表单后点击「生成报告」
- 点击图表中的某个项目并要求 AI 解释

操作结果会成为当前对话的新输入。

### Host Interaction（宿主交互）

用户操作会调用聊天应用自身提供的功能。

例如：

- 复制文本
- 打开网页
- 打开对象详情
- 执行允许的应用内操作

这三种交互可以在同一套界面中同时存在。

## 四、与普通 HTML 的区别

从视觉表现来看，Generative UI 可以使用 HTML、CSS、SVG 等技术实现。

但概念上，它和普通 HTML 有明显区别。

| 普通 HTML 内容 | Generative UI |
|---|---|
| 主要用于展示网页内容 | 用于构建 AI 对话中的交互界面 |
| 通常独立于聊天系统 | 与当前对话上下文关联 |
| 可以具有本地交互 | 同样支持本地交互 |
| 不一定能操作聊天系统 | 可以触发新的对话 |
| 不一定能访问宿主提供的功能 | 可以调用获得授权的宿主动作 |
| 通常由开发者预先设计 | 可以由 AI 根据问题动态生成 |

**Generative UI 的关键不在于采用哪种渲染技术，而在于生成的界面能够与 AI 对话系统形成双向交互。**

## 五、期望的使用体验

理想情况下，用户不应该需要主动要求 AI「生成一个交互界面」。

AI 应该能够自然判断什么时候使用 UI 更合适。

例如：

**场景 A：普通知识问答**

用户询问一个概念。

AI 正常输出 Markdown 解释。

不需要生成交互界面。

**场景 B：需要用户选择**

用户询问多个方案的区别。

AI 可以展示方案卡片和选择按钮。

用户点击某个方案后，AI 继续介绍对应内容。

**场景 C：需要实时调整参数**

用户询问某个计算问题。

AI 生成包含滑块和输入框的计算工具。

用户可以不断调整参数，并实时查看结果。

**场景 D：复杂数据分析**

用户提供一组数据。

AI 生成带有图表、筛选器和统计信息的数据面板。

用户可以在界面中探索数据，也可以选择某部分数据让 AI 继续分析。

**场景 E：多步骤交互**

AI 可以通过连续的交互界面逐步收集用户需要提供的信息。

例如：

选择项目类型 → 设置参数 → 确认需求 → 生成方案。

整个过程不需要用户反复手动组织文字。

## 六、适用的产品环境

目标产品同时具有：

- 网页版聊天界面
- 独立客户端
- 两端共用的后端服务
- 统一的 AI 对话系统

期望两端都能够支持 Generative UI，并尽可能保持一致的功能和交互体验。

这意味着 Generative UI 应被视为整个聊天系统的一项通用能力，而不是只属于某个特定前端的功能。

不同客户端可以采用各自适合的渲染方式，但对用户呈现的交互能力应尽量一致。

## 七、关于模型上下文与 Token 成本

还有一个重要目标：

**不希望为了支持 Generative UI，在每一次 AI 请求中都注入庞大的组件 API 文档。**

不希望要求模型掌握几十种自定义组件，以及每个组件复杂的属性、嵌套规则和事件接口。

期望方案具有以下特点：

- 尽可能减少 System Prompt 的长度
- 不需要为每个基础 UI 控件提供冗长定义
- AI 可以灵活生成多种类型的界面
- 简单 UI 不应该需要大量输出 Token
- 不应过度限制 AI 对界面布局和交互形式的创造能力
- 可以充分利用 HTML、CSS、SVG 等成熟的界面描述能力
- 交互界面应能够复用宿主提供的通用能力

这里不预先限定必须使用某一种 UI 协议或技术方案。

重点是兼顾**生成自由度、交互能力、跨客户端一致性和 Token 成本**。

## 八、最终目标

希望 AI 聊天不再局限于：

**用户提问 → AI 输出文本 → 用户阅读 → 用户再次输入。**

而是可以自然转变为：

**用户提问 → AI 根据需要生成交互界面 → 用户直接操作 → 界面本地响应或触发后续 AI 对话。**

其中最重要的几个特征是：

1. AI 可以动态生成界面，而不只是输出 Markdown。
2. 界面可以包含多种可交互元素。
3. 界面拥有本地状态，可以独立处理简单操作。
4. 界面可以主动向当前 AI 会话发送新消息。
5. 界面可以调用宿主应用明确允许的能力。
6. 多个控件可以组合成复杂的小型交互应用。
7. 网页版和独立客户端共享统一的对话后端。
8. 不希望引入非常庞大的 System Prompt 或组件定义。

**最终希望实现的是：让 AI 的回答从静态内容升级为能够操作、能够反馈、能够继续推动对话的动态交互内容。**
